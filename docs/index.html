What is in the core

piecewhat it does
gk_loopaccumulator, a 0.25 s frame clamp, a 240-step cap, alpha out for interpolation
gk_scenesnamed scenes with enter / exit / update / render; an unknown name is refused
gk_inputdown and pressed-this-frame, driven by the host — no engine types in the core
gk_savemagic + version + CRC32, so a half-written save is caught rather than loaded
gk_ecsentities, component bags and systems over a bitmask, fixed capacity, no malloc
gk_rngmulberry32 — the same sequence as game-kit's rng(), verified to 1e-12

Why not archetype storage

Measured with make bench. The ratio is real; the absolute numbers are not — at 256 entities a system run is 2.1 µs against 0.12 µs in a 16.6 ms frame.

entitiesscan ns/entityarchetype ns/entityratio
2568.10.4617.7×
1,02417.20.4736.6×
4,0968.92.184.1×

The first run of that benchmark showed 260 ns/entity — a linear id lookup inside every component access, so every system was O(n²). Systems now receive the entity, access is O(1), and the number fell to 8.1 ns.

Why it tests without an engine

The core has no raylib in it. main.c compiles with -DGK_NO_MAIN and then contains no engine at all, so the suite drives the real game loop, the real scene machine and the real ECS headless — no window, no display, no GPU. The stub in stub/ mirrors raylib 5.x signatures, so the same source builds both ways.

What was not verified where this was written: the real raylib link. raylib needs X11 and GL headers, so make and make size are the two things to run on a machine with raylib installed. The suite and the raylib-facing half were both compiled; the engine was not linked.

The demo game

Three scenes — title, play, over — with a player and six drifting motes, all entities in the ECS. Collection is an AABB test, the round is 30 seconds, and the best score is saved to disk. Every part of the core is exercised by the game, which is why the tests can assert on the game rather than on toy inputs.
